# AGENTS.md

Инструкции для работы в `Boris-Particle-Pusher`. Аудит выполнен 2026-09-27 по текущему рабочему дереву, истории Git, исходникам, сборке и сохранённым JSON. Описанное текущее состояние не следует путать с планом развития. При изменении архитектуры обновлять этот документ вместе с кодом.

## 1. Project Overview

Магистерская диссертация посвящена исследованию и оптимизации алгоритма Бориса для численного моделирования физики плазмы под RISC-V, в том числе RVV, с распараллеливанием на системе с общей памятью через OpenMP. Проект служит вычислительным бенчмарком: сравниваются AoS/SoA, скалярное и векторное исполнение, число потоков, флаги компилятора и размещение потоков.

Реализован релятивистский шаг движения заряженной частицы в заданных электромагнитных полях: электрический полутолчок, магнитное вращение, второй электрический полутолчок и перенос координаты. При нулевом электрическом поле магнитное вращение сохраняет модуль импульса с учётом погрешности округления. Это ядро движения частиц, а не полный PIC-код: здесь нет сеточного решателя полей, интерполяции, осаждения токов, столкновений или самосогласованного расчёта плазмы.

Фактический стек: C++17, CMake >= 3.14, OpenMP, GCC-совместимые расширения `__restrict`, RVV intrinsics из `<riscv_vector.h>`, Google Test 1.12.1, Google Benchmark 1.8.3. Python/Matplotlib используются для графиков; старый `plots.py` также импортирует NumPy. Собственных исходников C и Fortran сейчас нет. Kokkos, SYCL и Coarray Fortran — будущие направления, а не готовые backend-реализации.

### Данные и выполнение шага

- `Particle` хранит `pos`, безразмерный импульс `u`, заряд `q`, массу `m`, кэшированный `gamma`. Конструктор принимает **физический** импульс и делит его на `m*c`; `setU()` обновляет `gamma`.
- AoS — `std::vector<Particle>`. SoA — восемь независимых `std::vector<double>`: `x/y/z`, `ux/uy/uz`, `q/m`; число элементов дополнительно хранится в публичном `size`. Кэша `gamma` в SoA нет.
- `Field` состоит из двух `Vec3`: `E` и `B`. Обе пакетные функции получают одно общее неизменяемое поле для всех частиц. Полей на сетке или массива полей в этом API нет.
- AoS распараллеливается через `#pragma omp parallel for schedule(static)` в обоих `.cpp`. SoA на x86 и резервный RISC-V путь используют `parallel for simd schedule(static)`.
- RVV SoA создаёт одну `omp parallel`-область на вызов, вручную делит `N` с распределением остатка между потоками. Каждый поток обрабатывает свой диапазон порциями `__riscv_vsetvl_e64m1(end-i)` с `vfloat64m1_t`; фиксированный VLEN в ядре не зашит. Загрузки, арифметика, `sqrt`, деления и записи выполняются intrinsics; используются FMA.
- Барьер на выходе из OpenMP-области завершает шаг. Бенчмарк вызывает пакетную функцию заново на каждом временном шаге, поэтому накладные расходы запуска параллельной области входят в измерение.

### Сборка и RISC-V

`BorisPusherLib` — статическая библиотека. Заголовки и исходники собираются через glob; два платформенных `.cpp` исключаются из общего списка, после чего добавляется ровно один. RISC-V определяется через `CMAKE_SYSTEM_PROCESSOR` (`riscv64|RISCV64|rv64gcv`) либо имя компилятора с `riscv64`; любой другой процессор получает файл с именем `x86`.

Библиотека экспортирует `-O3` через `PUBLIC`, в том числе в тесты и Debug-сборки. Для RISC-V дополнительно принудительно экспортирует `-march=rv64gcv`. OpenMP обязателен (`find_package(OpenMP REQUIRED)`). `-ffast-math`, `-march=native`, `-mprefer-vector-width=512`, `-mabi` в действующих compile options не заданы; комментарии об автоматическом наследовании fast-math устарели. Упомянутого в CMake кластерного `build_all_riscv.sh` в проекте нет.

Google Benchmark и Google Test загружаются безусловно через FetchContent с тегами `v1.8.3` и `release-1.12.1`; отдельные выключатели тестов/бенчмарков не предусмотрены. `gtest_discover_tests` использует `PRE_TEST`. `UnitTest` имеет собственный `main`, хотя линкуется с `gtest_main` — избыточность, а не подтверждённая ошибка линковки.

Важное ограничение: `CMAKE_RUNTIME_OUTPUT_DIRECTORY` установлен в `${CMAKE_SOURCE_DIR}/bin`. Даже разные каталоги `-B` сейчас могут перезаписывать одни и те же бинарники; простое `-DCMAKE_RUNTIME_OUTPUT_DIRECTORY=...` не исправляет обычный `set` в CMakeLists. Не смешивать host- и cross-сборки в существующем cache или общем `bin`.

На дату аудита `build/CMakeCache.txt` указывает Release, `/opt/riscv/bin/riscv64-unknown-linux-gnu-g++`, `CMAKE_CROSSCOMPILING_EMULATOR=qemu-riscv64`. `file bin/UnitTest bin/PerfTest` подтверждает ELF RISC-V. Версия cross-компилятора 15.1.0 указана в локальных настройках редактора; это не универсальное требование проекта. Переносимого toolchain-файла, presets и CI нет.

### Полный предыдущий отчёт и уже выполненная работа

`previous_report.md` — полный отчёт предыдущего семестра, а не краткая заметка. Он содержит теорию в СГС, вывод схемы Бориса, четыре группы Google Test, структуру AoS/SoA, CMake и cross-build, OpenMP/RVV-реализацию, методику Google Benchmark, x86 NUMA-эксперименты, сравнение с pyHiChi, RISC-V эксперимент, заключение, литературу и приложения с копиями исходников. Считать его историческим описанием уже выполненного этапа диссертации; новые изменения должны уточнять его, а не стирать достигнутые результаты.

По отчёту и предоставленным сведениям уже выполнены следующие этапы:

- Для x86 использовался двухсокетный узел Intel Xeon Silver 4310T: 2 сокета × 10 физических ядер × 2 SMT-потока, всего 40 логических CPU; NUMA — 2 узла; L1d 48 KiB, L1i 32 KiB, L2 1280 KiB, L3 15360 KiB на сокет. В отчёте также указаны 64 GiB DDR4, CentOS 7, GCC 9.5.0, CMake 4.3.3 и Ninja 1.12.1. Переданные данные `lscpu` подтверждают модель, топологию, caches, диапазон 800–3400 MHz и AVX-512 flags; базовая частота не означает частоту конкретного benchmark-прогона.
- Запрос вычислительного узла выполнялся через SLURM (`srun -N 1 -n 1 -c 1 -t 00:02:00 lscpu`). Performance job использовал `submit_benchmarks.sh` с `--cpus-per-task=40`, `--exclusive`, `SLURM_CPU_BIND=none`, `OMP_PLACES=cores`/`OMP_PROC_BIND` и, кроме режима `pure`, `numactl --interleave=all`.
- Для pyHiChi собирались отдельные `O3`, `O3_fastmath`, `O3_fastmath_native` бинарники. Сравнение проводилось на C++ benchmark target pyHiChi, а не через Python API.
- RISC-V запускался на отдельной машине/очереди `k1` через общую файловую систему. Узел: Spacemit X60, 8 CPU, 8 ядер в одном сокете, 1 поток на ядро, max 1600 MHz, min 614.4 MHz, L1d/L1i по 256 KiB (8 экземпляров), L2 1 MiB (2 экземпляра). Cross-build выполнялся на кластере GCC 15.1.0; `submit_benchmarks_riscv.sh` задаёт `--cpus-per-task=8`, `--partition=k1`, `--exclusive`, `OMP_PLACES=cores`, `OMP_PROC_BIND=close` и не использует NUMA interleave.
- `build_all_riscv.sh` собирает `rvv_scalar` (`-march=rv64gc`), `rvv_vector` (`-march=rv64gcv`) и `rvv_vector_fastmath` (`-march=rv64gcv -ffast-math`). Последняя конфигурация определяется одновременно CMake и явным флагом. Это объясняет происхождение сохранённых RISC-V бинарников, но не устраняет текущую проблему общего `bin/` и CMake, принудительно добавляющего `-march=rv64gcv`.
- Масштаб benchmark-файлов: `N=1,000,000`, `steps=1,000`, одна benchmark iteration, то есть `10^9` обновлений частиц на случай. Сохранены серии для AoS/SoA, 1/2/4/8/16/32/40 потоков на x86 и 1/2/4/8 на RISC-V.
- Исторический тезис отчёта для x86: на `O3_fastmath_native` SoA около 5.9 s против AoS около 17.5 s на одном потоке, около 3× для этой серии. Для RISC-V отчёт округляет scalar SoA около 450 s и vector/vector+fast-math около 100 s, то есть примерно 4.3–4.4× по сохранённым JSON, а не строгие 4.5×.
- Исторический тезис отчёта для NUMA: `close`/`nobind` были лучшими в отдельных сериях на 40 потоках, `spread` достигал примерно 1.9 s. Это измеренный эффект политики запуска, но не доказательство конкретной причинной цепочки (cache thrashing, UPI или memory-bound) без perf/NUMA counters.
- В отчёте заявлены objdump-проверки AVX-512/RVV и запуск тестов на RISC-V/QEMU, однако в текущем workspace нет воспроизводимых логов этих проверок и точного подтверждения запуска unit-тестов на Banana Pi. До появления логов считать их заявленными этапами отчёта, но не подтверждёнными текущим аудитом.

При дальнейшей редактуре отчёта сохранять его результаты, но осторожно формулировать следующие тезисы: `10^-13` — допуск части тестов, не всей верификации; `std::vector` не гарантирует специальное SIMD-выравнивание; AVX-512 в x86 получается через compiler auto-vectorization, а не через явные intrinsics; четыре `double` в VLEN=256 не являются теоретическим пределом общего speedup; «близкое к линейному» масштабирование RISC-V не следует из серии 106.3 s → 25.4 s на 8 потоках; причины NUMA-наблюдений нужно отделять от измеренного факта.

### Тесты и проверенный способ запуска

В собственных тестах проверяются ускорение в E и половина циклотронного оборота (`1e-3` относительная ошибка), сохранение `u²` одной частицы и SoA-пачки из 16 частиц (`1e-13` абсолютная ошибка). Последний допуск относится к конкретным тестовым величинам, а не к любым энергиям и длительностям моделирования.

### Технический долг и ограничения интерпретации

1. **Скалярный RISC-V эксперимент пока нельзя надёжно воспроизвести текущим CMake.** Принудительный `-march=rv64gcv` конфликтует с намерением выбрать `rv64gc`; `<riscv_vector.h>` включён вне `#ifdef`. Нужны явный выбор ISA/backend и проверка compile command. Имя `rvv_scalar` в JSON не доказывает отсутствие векторных инструкций в бинарнике.
2. **Исходные задачи двух бенчмарков отличаются.** Здесь одно поле на весь массив и `mt19937_64(1)`; pyHiChi использует `rand()` и массив полей, причём `minField.z=maxField.z=10`, поэтому обе z-компоненты поля фиксированы. Есть дополнительный трафик полей, весов/типов/gamma и иная организация доступа. Одинаковый seed не означает одинаковые частицы. Комментарий «в точности как в pyHiChi» неверен.
3. **Физические константы не полностью совпадают.** Здесь `MASS_E=9.10938356e-28`, там `electronMass=9.10938215e-28`; заряд и c совпадают. Физические импульсы порядка `[-10,10]` в СГС дают электронам очень большие `u`, а не порядок единицы. Это допустимая вычислительная нагрузка, но не заменяет набор тестов разных физических режимов.
4. **Методика времени требует уточнения.** Оба бенчмарка используют `Iterations(1)`, не вызывают `UseRealTime()`. Собственный `MParticles/s` рассчитывается механизмом rate по выбранному Google Benchmark времени; сохранённые значения соответствуют `cpu_time`, а графики используют `real_time`. Для OpenMP сравнивать wall time и вычислять throughput согласованно; не смешивать эти столбцы. Поле JSON `threads=1` описывает потоки Google Benchmark; OpenMP-потоки записаны в имени benchmark как третий числовой аргумент.
5. **Недостаточно метаданных и статистики.** Все 27 JSON читаются; единицы в них — секунды. x86-файлы содержат по 14 записей (AoS/SoA × 1,2,4,8,16,32,40), RISC-V — по 8 (× 1,2,4,8). Контексты указывают `node1.nngu`/40 CPU и `k1node3`/8 CPU. Повторных серий, commit+dirty hash, полных compiler flags, OMP environment и NUMA-команд в них недостаточно для строгого воспроизведения. По числу CPU нельзя заключать число физических ядер. На x86 записан включённый frequency scaling; фоновые load averages ненулевые.
6. **Графики содержат неподтверждённые допущения.** CPU-модели, AVX-512 и трактовка `pure/nobind/close/spread` зашиты в скрипт; исходных launch-скриптов нет. График 7 сравнивает scalar с vector+fast-math, смешивая два фактора; линия «теоретический предел 4x» не является доказанной границей ускорения всего ядра. Межплатформенное сравнение показывает комбинацию железа и сборки, а не чистый эффект ISA.
7. **Парсер графиков хрупкий.** `make_plots.py` предполагает секунды и фиксированное имя benchmark, не учитывает repetitions/aggregate records, перезаписывает словарь по числу потоков и теряет различия N/steps. При отсутствии ожидаемых наборов возможны неопределённый `threads_list` и KeyError. Пути зависят от cwd, импорт создаёт/перезаписывает графики. Старый `plots.py` вообще не связан с JSON.
8. **Покрытие физики неполное.** Нет прямого сравнения AoS/SoA/RVV по всем координатам и импульсам, теста пакетного AoS, нулевого поля, нейтральной частицы, смешанных q/m, долгого сохранения энергии, сходимости по dt и RVV-хвостов. Сохранение нормы само по себе не проверяет направление вращения и фазу. Комментарий про случайную SoA-пачку скрывает фактически детерминированные данные.
9. **Инварианты данных не защищены API.** Публичные SoA-векторы могут расходиться с `size`; `resize(N)` создаёт нулевые массы до заполнения. Можно напрямую изменить `Particle.u` без обновления `gamma`. Не проверяются m>0 и конечность значений. Проверки предусловий следует располагать вне измеряемого горячего цикла.
10. **Смешаны обязанности и дублируется код.** Один заголовок объединяет векторы, данные, константы и физику; OpenMP подключён в публичном header. Скалярный SoA-код дублируется в двух `.cpp`, AoS-обёртка тоже. `utests.hpp` без guard содержит определения тестов; при добавлении новых translation units его нельзя бездумно включать повторно. Удалять закомментированные прототипы только отдельной осмысленной правкой, сохранив полезную историю в Git.
11. **Предполагаемые узкие места требуют измерений.** Два sqrt, деления, трафик восьми массивов, создание OpenMP-области на каждом шаге, последовательный first-touch при инициализации на NUMA. Они видны в коде, но профиль, roofline и отчёты векторизации для текущих сборок не приложены; не объявлять ядро memory-bound без проверки.
12. **Воспроизводимость и сопровождение.** Кластерные скрипты сборки/запуска, toolchain/presets, Python dependency manifest отсутствуют. Исторические результаты смешаны с бинарниками. Gitignore скрывает локальную конфигурацию, важную для запуска. Текущие `-O3` PUBLIC, glob и общее `bin/` мешают независимым Debug/Release/ISA-конфигурациям.
13. **Избыточность cluster scripts.** `build_all_my.sh` и `run_my_pipeline.sh` частично дублируют x86-сборку, но задают разные флаги и наборы режимов; `run_my_pipeline.sh` не запускает `pure`, а `build_all_my.sh` добавляет `-g` и отчёты векторизации. `submit_benchmarks.sh` — более полный SLURM-вариант и включает pyHiChi. `build_pyhichi.sh` вызывает внешний `build_pyhichi_cluster.sh`, которого в текущем репозитории нет. Эти файлы полезны как журнал исторического workflow, но перед повторным экспериментом их нужно свести к одному документированному pipeline и убрать опасные `rm -rf` по именованным build-каталогам.

## 3. Constraints & Physics Rules

**Запрещено искажать математику Бориса ради оптимизации или прохождения тестов.** При структурном рефакторинге сохранять текущие формулы и смысл переменных. Опорная реализация — `bp::BorisPusher` в `include/BorisPusher.h`; она не заменяет независимых аналитических проверок. Обнаруженную физическую ошибку оформлять отдельно, не прятать её исправление в переносе кода.

Используется СГС: x в см, t в секундах, m в граммах, q в статкулонах, E в статвольт/см, B в гауссах. Текущие константы: `c=29979245800.0`, `m_e=9.10938356e-28`, `q_e=-4.80320427e-10`, `PI=3.141592653589793`. Не менять систему единиц, знаки заряда или значения констант как побочный эффект выравнивания с pyHiChi.

Безразмерный импульс `u=p_phys/(m*c)=gamma*v/c`, `gamma=sqrt(1+u·u)`, `v=c*u/gamma`. Это не скорость и не физический импульс. Контракт одного шага:

```text
a         = q*dt/(2*m*c)
u_minus   = u_old + a*E
gamma_m   = sqrt(1 + u_minus·u_minus)
t         = a*B/gamma_m
s         = 2*t/(1 + t·t)
u_prime   = u_minus + u_minus × t
u_plus    = u_minus + u_prime × s
u_new     = u_plus + a*E
gamma_new = sqrt(1 + u_new·u_new)
x_new     = x_old + dt*c*u_new/gamma_new
```

- Сохранять порядок векторных произведений, оба электрических полутолчка, вычисление магнитной gamma по `u_minus` и перенос координаты по новой скорости. Не заменять их старой gamma/скоростью. Интерпретация leapfrog требует согласованных временных уровней начальных условий; не менять их незаметно.
- Не подменять релятивистский Boris нерелятивистским, Vay, приближённым вращением или radiation reaction. При `E != 0` энергия может меняться; требование сохранения `u²` относится к чисто магнитному шагу.
- Сохранять `double` в базовом режиме. FMA, обратные величины и перестановка арифметики могут менять округление: RVV уже использует FMA. Требовать согласования в обоснованном допуске, а не обещать побитовое совпадение платформ.
- `-ffast-math`, приближённые reciprocal/sqrt и смена точности — отдельные экспериментальные конфигурации с проверкой ошибки. Не ослаблять тестовые допуски только ради успешного оптимизированного прогона.
- Поддерживать равенство длин всех SoA-массивов и `size`, положительные массы, согласованность `u/gamma`; сохранять q/m в ходе push. Для `__restrict` не допускать перекрытия массивов.
- Параллельные реализации записывают только собственные частицы; поле доступно для чтения. RVV должен корректно обрабатывать N=0, N<числа потоков, N не кратное VL и все хвосты; не фиксировать длину вектора по параметрам одной платы.
- Любой новый backend проверять на одних исходных данных против scalar-reference и аналитики, затем измерять скорость. Инициализацию, выделение памяти и переносы данных учитывать явно и одинаково в сравниваемых сценариях.

Coarray images не считать автоматически эквивалентом OpenMP threads: описать runtime, модель памяти, размещение images и стоимость синхронизаций, чтобы сравнение соответствовало теме общей памяти.
9. **Автоматизировать регрессии.** Host CI: configure/build/CTest и короткие smoke-бенчмарки без порогов по шумному времени; отдельные задания cross-build и проверки RVV. Численные инварианты обязательны для каждого backend и math-профиля. Строгие performance-серии запускать на закреплённых узлах с описанным окружением и архивированием исходных JSON.

Изменение считается готовым после проверки соответствующего backend, сохранения физических допусков и фиксации того, что действительно запускалось. Не выдавать host-тесты за проверку RVV, регистрацию бенчмарков — за измерение скорости, а график — за доказательство корректности физики.
